# WODLog 아키텍처

## 워크트리 작업 지도

기준 코드 `5ef3cff`. WODLog는 Flutter와 Riverpod, go_router, Drift로 구성된 로컬 우선 앱이다. UI는 provider를 통해 repository 또는 성장 서비스에 접근한다. 네이티브 SQLite와 Safari의 Drift WebAssembly DB는 각각 기록을 보관한다.

| 대제목 | 이슈 | 담당 범위 |
| --- | --- | --- |
| UI · 화면과 사용자 경험 | #8, #9, #11, #14 | Flutter 화면, 단위 입력·표시, 번역·RTL, 런처 아이콘 |
| BACKEND · 로컬 데이터와 운동 규칙 | #6, #12, #16, #17 | 로컬 저장·이관, 내보내기, 성장 계산, WOD 비교 계약 |
| RELEASE · 빌드·배포와 실기기 검증 | #1, #3, #4, #10, #13, #15 | 서명·배포·실기기 검증과 스토어 준비 |
| OCR · 사진 인식과 기록 초안 | #5 | 기기 내 사진 인식, 초안 검토, 확인 후 저장 |

### 병렬 작업 및 통합 순서

- #16/#17은 데이터 계약을 독립적으로 작업한다. #11은 기존 화면 검증을 시작하고 각 계약이 확정되면 UI를 연결한다.
- #8이 설정 라우트와 화면 골격을 먼저 제공한다. #6이 JSON 파일 입출력 경계를 잡은 뒤 #12를 설정 화면에 연결한다. #8과 #11이 함께 수정하는 `progress_screen.dart`는 먼저 준비된 PR을 병합한 후 다음 PR을 리베이스한다.
- #9의 검증은 병렬로 시작한다. 공용 ARB와 생성 번역 파일은 각 기능의 키를 먼저 병합하고 #9가 최종 점검한다.
- `app_database.dart`, 테이블, Drift 생성 파일의 변경이 필요할 때 로컬 데이터 담당이 하나의 마이그레이션으로 통합한다. `pubspec.yaml`·잠금 파일과 플랫폼 설정을 공유하는 변경은 먼저 병합된 PR을 기준으로 리베이스한다.
- #1 → #3 순서로 iOS 베타를 준비한다. #4, #10, #15의 기기 검증은 각각 Galaxy, iPhone 네이티브, iPhone Safari로 진행한다. #14의 런처 리소스는 서명 워크플로와 분리한다. #13은 비공개 테스트 후 진행한다.
- #5와 #17에서 WOD 저장소를 함께 바꿔야 할 경우 #17 조회 계약을 먼저 합의한다.

### 구현 기준

- 현재 DB는 스키마 v1, 테이블 6개를 사용한다. 세션 날짜는 로컬 날짜 문자열, 중량은 nullable kg, 세트 번호는 종목 항목 내 유일하다. 앱의 운동 기록에는 계정이나 서버가 필요 없다.
- PR과 날짜별 추이는 원본 세트에서 계산한다. 실제 PR과 추정값을 구분한다. Epley에 성공한 2~10회 세트를 사용하는 것은 #16의 설계 제안이다.
- JSON은 버전과 ID·관계를 보존하고 사전 검증 후 단일 트랜잭션에서 복원한다. #6은 기존 기록 사전 백업과 전체 교체 흐름을 구현 전 검증한다.
- WOD 비교는 결과 유형과 확인된 운동 구성이 맞을 때만 제공한다. OCR은 사용자 확인 후 저장한다.
